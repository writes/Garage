- purchase() rechecks identity, but LiveReceiptCreditsStoreClient.purchaseCredits() performs another awaited product fetch before StoreKit. RC/Firebase identity can change in that gap; the transaction may be attributed to one UID and persisted under another.
- A successful purchase with a nil transaction ID has no durable marker. If the one immediate quota refresh is early, reopening resets to idle and offers Buy again while the first charge/grant is unresolved; transaction-specific repair is impossible.
- paymentPending returns the controller to idle and persists no pending state. Repeated taps or sheet reopens can create multiple Ask-to-Buy/SCA requests for a consumable, later yielding unintended multiple charges.
- At 72h, a successful reconcile returning unknown is treated as a definitive miss: the only transaction key is deleted, purchaseState remains idle, and the UI shows support text plus Buy. Server absence does not prove the user was not charged.
