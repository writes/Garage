### Blocking findings

- At TTL, pollOnce turns auth/network/429/5xx/cancellation/UID-switch failures into false; resumeOutstandingMarkers then marks the purchase missing and deletes its only transaction ID. A transient failure can irreversibly destroy paid-purchase recovery.
- A success with no transaction ID is neither persisted nor retried. The purchaser returns completed("") even if identity changed, and awaitGrant leases the post-switch UID, so it can apply another account's quota while losing the payer's recovery path.
- Non-cancel RevenueCat errors immediately restore idle with no durable uncertain-purchase state. If StoreKit completed but SDK/validation reporting failed, Buy is re-enabled without a marker, allowing a second consumable charge.
- After an expired unresolved purchase, purchaseState remains idle: the support notice and Buy button render together after the transaction key was deleted. The app can solicit another charge before the first paid transaction is resolved.

### Advisory findings

- ReceiptCaptureView awaits the uncapped sweepIncomplete loop before creating the controller or resuming markers. A stale flag can indefinitely block paid-grant repair; backoff limits request rate but not starvation, and caught cancellation does not stop outer setup.
- All accounts' UIDs and transaction IDs share one UserDefaults JSON blob; decode failure silently discards the full repair queue without migration or an error signal. This is purchase-history metadata, not a secret, but its durability and privacy handling are weak.
- Localized StoreKit pricing fixes the prior 3.1.1 issue, but making a new pack repay a refund deficit before delivering credits remains a consumer and App Review risk. Obtain explicit policy approval and ensure support/refund handling is non-coercive.
- Tests omit TTL network/cancellation failure, Firebase switching inside purchase, indeterminate SDK errors, and stuck-sweep cancellation; the named Firebase mid-purchase test only switches before a second call. No current-head build/test receipt is supplied.
- phase, quotaFailure, and notAReceiptBlocked setters are widened module-wide to support recovery, weakening the hardened capture state machine. Keep them private and expose a narrow recovery transition.

### Blocking findings

- For expired markers, `pollOnce` returns `false` on a transient network error. `resumeOutstandingMarkers` treats this as a definitive miss, permanently destroying the transaction ID via `markExpiredUnresolved`. You must distinguish between a successful empty reconcile and a network timeout.
- If identity diverges during a purchase that yields a nil transaction ID, `ReceiptCreditsPurchaser` incorrectly returns `.completed("")`. `awaitGrant` then erroneously attempts balance recovery for the wrong user account. Return `.identityChangedAfterPurchase` on any identity divergence.

### Advisory findings

- The UI copy for an expired unresolved purchase instructs the user to 'Pull to refresh', but `ReceiptCaptureView` does not implement the `.refreshable` modifier. Users cannot pull to refresh and must manually close and reopen the sheet. Update the copy to reflect actual capabilities.
- `resumeOutstandingMarkers` calls `reconcileCreditPurchase` unconditionally on every sheet appearance for all active markers. This hammers the server's mutation endpoint for transactions that are still in flight. Restrict reconcile to the end of the polling window or marker expiry.
- When an active marker remains unresolved on resume, `purchaseState` is set to `.delayed` with no ongoing background polling. If the webhook arrives while the sheet is open, the UI remains blocked until the user manually dismisses and reopens the sheet. Add polling or clarify behavior.
