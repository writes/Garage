# Receipt/Invoice Capture — Final Implementation Plan

**Date:** 2026-07-28
**Status:** APPROVED DESIGN — judge panel selected Design 2 (product-first) 3/3, tally 156/157/176. This document is the winning design as the spine with the best-judged ideas from Designs 0 (mvp-first) and 1 (accuracy-first) grafted in, and every judged defect resolved against verified repo truth.
**Feature:** User photographs (or imports a PDF of) a shop receipt/invoice → Claude parses it into a prefilled entry (type, odometer, cost, shop, date, notes/line items) → user confirms in the entry form. **Trust Pledge: AI only prefills, never commits.**
**Pattern lineage:** Voice Quick-Add shape (capture sheet → strict forced-tool parse → one-shot AppRouter prefill → user confirms), NOT the oil-analysis in-form coordinator — parsing completes before the entry form exists, so the mutation-gating/epoch/quarantine machinery is unnecessary by construction.

## 2. Architecture (spine, verified against repo)

```
EntryTypePicker ("Scan a Receipt", under "Speak an Entry")
      │  router.present(.receiptCapture)   [zero-vehicle gated, FormKind.receiptCapture]
      ▼
ReceiptCaptureView / ReceiptCaptureViewModel
   sources: Camera (new CameraPicker) · PhotosPicker · fileImporter(.pdf)
   preflight: ReceiptPreflighter
     images → parse variant 1568px JPEG q0.85 (scale=1) + attachment variant via
              AttachmentImageProcessor.downsampledJPEG (2048px q0.8, color)
     pdf    → OilAnalysisPDFPreflighter.readValidatedBase64 core + security-scope lease
   ≤2 pages/images per scan ("Add page")
      │  ReceiptQuickAddService.proposeEntry(...)  →  callable receiptQuickAdd
      ▼
CloudFunctions receiptQuickAdd.ts (claude-haiku-4-5, forced strict tool, sanitizer)
      │  ReceiptEntryProposal
      ▼
router.presentReceiptPrefilledForm(ReceiptPrefillPackage{ proposal, attachments })
      │  one-shot pendingReceiptPrefill (parallel to pendingVoicePrefill, kept separate)
      ▼
EntryFormScaffold .task → consumeReceiptPrefill() → applyReceiptPrefill (+ReceiptPrefill ext)
   seeds fields · joins lineItems into notes · stages attachments (Pro) ·
   odometer-floor reconciliation · wasReceiptSeeded
      ▼
User reviews → Save → uploadPendingAttachments (existing pipeline) → receipt_entry_confirmed
```

Disclosure copy on the capture sheet (oil-analysis consent precedent): *"Sent to Claude (Anthropic) to draft your entry. AI can make mistakes — you review everything before saving."*

**Odometer-floor reconciliation (the shipped-defect risk only Design 2 caught, verified):** `Validators.odometer` rejects any value below `lastKnown` (Validators.swift:26–28), wired at EntryFormViewModel.swift:129 via `odometerFloor` (+EditPrefill.swift:34). The flagship use-case is backfilling OLD receipts whose mileage is below current — a naive prefill hard-blocks Save. Fix: after `prepare()` loads the floor, if `wasReceiptSeeded && prefilledOdometer < odometerFloor` → clear the odometer field and append `"Odometer on receipt: N mi"` to notes. Save is never blocked; the data point survives in the dossier.

**Model:** `claude-haiku-4-5` (unsuffixed, matching both siblings). Receipts are high-contrast printed documents — the easiest vision class — and the repo's own evidence (voiceQuickAdd.ts:222–224: Haiku+few-shot 97.8% vs Sonnet-no-few-shot 85.5%) shows prompt+few-shot+strict-tool, not model tier, carries extraction accuracy here. Escalation to `claude-sonnet-4-6` is a one-line model-constant change, permitted **only** by the pre-registered golden-eval gate (§7). Cost: ~2 pages ≈ 3–4K input tokens ≈ $0.005–0.01/scan on Haiku; worst-case fully-utilized Pro user ≈ $0.20/day.

**No protected surfaces touched:** `NSCameraUsageDescription: "Attach receipts and vehicle photos."` and `NSPhotoLibraryUsageDescription` already ship in project.yml (verified, Info.plist properties block). No rules/firebase.json/CI changes; `usage_quotas` is admin-SDK-only; attachments ride the existing Storage path. `Garage.xcodeproj` regenerated via pinned `.tools/bin/xcodegen` (ALLOWED; regen-equality gate promotes). Cloud Function deploy stays operator-gated (Law 5).

## 4. Server function — `CloudFunctions/src/functions/receiptQuickAdd.ts`

Structural clone of voiceQuickAdd.ts: `onCall({ region: "us-central1", enforceAppCheck: true, secrets: [anthropicApiKey] })` wrapping a dependency-injected `receiptQuickAddRequest(request, { apiKey, db, fetchImpl, now })` for vitest. Imports `QuotaFirestore, isRecord, safeQuotaCount, nextUtcMidnight, userHasActiveProEntitlement` from claudeProxy and `VALID_ENTRY_TYPES, toolInputFromPayload, referenceDateLine` from voiceQuickAdd (cross-importing function modules is the established pattern).

**Request:** `{ images?: string[] (1–2 base64 JPEG), pdfBase64?: string, vehicle?: {year, make, model, currentOdometer} }` — exactly one of `images`/`pdfBase64`, else `invalid-argument`.

**Validation before any quota spend:** auth required; standard-base64 pattern check (claudeProxy's `isStandardBase64`); magic bytes decoded from the first ≤8 base64 chars only (`hasPdfMagic` technique) — **JPEG `FF D8 FF` only** for images (the client always re-encodes to JPEG; the PNG acceptance in Design 2 was surface its own client never used — removed), `%PDF-` for pdf; per-image ≤ 4 MiB base64; pdf ≤ 9 MiB base64 (matches `OilAnalysisPDFPreflighter.maxPDFBase64Bytes`, verified line 162); total payload ≤ 9 MiB (envelope headroom under the 10 MiB callable limit).

**Anthropic call:** model `"claude-haiku-4-5"`, `max_tokens: 1024`, forced strict tool_choice on `RECEIPT_ENTRY_TOOL`, **no extended thinking** (the API rejects thinking + forced tool — verified live, claudeProxy.ts:519). Messages: compact text-transcribed few-shot exchange (computed dates, `fewShotMessages` pattern) + one user turn with one `image`/`document` source block per page + a text block carrying `vehicleContextLine` + `"Extract this vehicle service receipt into a log entry."`

**System prompt** (each clause targets a receipt failure class; iterated under the golden eval, voice-style): read the GRAND TOTAL (never subtotal, amount tendered, or change); the odometer is the vehicle-mileage line, never an invoice number, RO number, phone number, ZIP, or VIN fragment — cross-check plausibility against the stated current odometer; use the SERVICE date, never a payment-due/statement/reprint date; converting printed text to digits is recording, not inventing (the voice chilling-effect lesson, pre-applied); an unreadable value is omitted, never guessed; a parts-only receipt with no labor lines suggests isDiy; set `documentLooksLikeReceipt=false` for anything that is not a vehicle service receipt or invoice. **Plus `referenceDateLine(now)` appended to the SYSTEM prompt** — the documented voice lesson (voiceQuickAdd.ts:214–217): without it the model hallucinates past years that the sanitizer accepts.

**Response handling:** shared `toolInputFromPayload` (most-populated tool_use block — documented live failure). Then:
1. If raw `documentLooksLikeReceipt === false` → `HttpsError("failed-precondition", "Not a service receipt.", { reason: "not_a_receipt" })`. **Quota kept** (inference was billed). (G1)
2. Recognizability backstop (mirrors `isRecognizableOilAnalysis`): require shopName OR finite cost OR entryDate present in the RAW input, else `internal` "unrecognized" — arbitrary schema-valid JSON cannot masquerade as success.
3. `sanitizeReceiptProposal(input, now)`: entryType clamped to enum else `"maintenance"`; cost 0..1,000,000; odometerReading 0..2,000,000; shopName ≤200 trimmed; notes ≤2,000; `clampEntryDate` (any past date allowed — backfill is the point; future beyond +36h dropped, voiceQuickAdd.ts:109–115 verbatim); isDiy boolean-or-null; lineItems → max **20** strings, each trimmed ≤160, non-string members dropped.

**PII (hard rule, both siblings verbatim):** no request content, no model output, no image/document bytes ever logged — status codes and classified reason names only (`error.name`, never `.message` for parse errors: V8 errors embed source snippets). Receipts are worse than transcripts: names, addresses, card last-4, VINs.

## 5. Quota + refund policy

**Model of record (pending tri-vote checkpoint A, §10):** free-lifetime teaser **3** + Pro daily **20**.
`FREE_LIFETIME_RECEIPT_QUOTA = 3`, `DAILY_RECEIPT_QUOTA = 20` — exported constants.

- Rationale (the judged-best monetization thinking): a receipt is the one artifact every prospective user is holding at evaluation time — the shoebox of them is WHY they downloaded the app. Three free scans let the magic land, then paywall at the highest-intent moment on Day 0 (launch research: 90% of trial starts are Day 0). 20/day (vs voice's 30) reflects vision cost ~5–10x a transcript while covering the realistic ceiling: a shoebox-onboarding session backfilling a decade of records — the exact scenario a 5/day cap (Design 1) would strangle. Per-request cap of 2 images bounds single-call spend. Free-teaser lifetime cost ≈ $0.03/user.
- **`consumeReceiptQuota`** — clone of the verified `consumeOilAnalysisQuota` dual-bucket single transaction (claudeProxy.ts:242–296; a profile change can never split entitlement selection from charging): read `users/{uid}` → `userHasActiveProEntitlement` → Pro bucket `usage_quotas/{uid}_receipt_{YYYY-MM-DD}` (kind `"receipt_quickadd"`) capped 20, else free bucket `usage_quotas/{uid}_receipt_lifetime` (kind `"receipt_quickadd_lifetime"`) capped 3.
- **Errors:** Pro exhausted → `resource-exhausted { reason: "receipt_daily_exhausted", resetAt: nextUtcMidnight(now) }`; free exhausted → `resource-exhausted { reason: "receipt_free_exhausted" }`. **No `permission-denied pro_required` path exists in this model** — free users are admitted for their 3 lifetime units. The client maps exactly the three server reasons (`receipt_free_exhausted` → paywall, `receipt_daily_exhausted` → reset-time message, `not_a_receipt` → retry copy); Design 2's vestigial `pro_required` client mapping is deleted (fix F4). If the tri-vote flips to Pro-only, the swap is mechanical: `consumeVoiceQuota` clone + `pro_required` fence + client `.proRequired → paywall` mapping.
- **Refund policy (identical to both siblings, enforced in exactly the same places):** refund only on fetch throw (network) or upstream HTTP ≥ 500 — Anthropic did not complete billable inference. Every other failure — 4xx (429 included), malformed JSON, no tool_use block, unrecognized output, **and `not_a_receipt`** — keeps its quota unit because inference was billed.
- **Client gating:** new `PaywallSource.receiptScan = "receipt_scan"` (auto-enrolled in the `allCases` dismissed-event coverage test). Capture row stays visible to free users (visible-upsell pattern). **Attachment interplay** (the cross-feature entitlement issue only Design 2 confronted): attachments are Pro-gated client-side (`EntryFormScaffold.attachmentsSection` → `ProGateView`, verified lines 121–126) AND server-side (`enforceAttachmentProGate` Storage trigger, verified). Receipt attachments are staged into `pendingAttachments` only when the user is Pro; a free teaser user gets the prefill plus one upsell line in the form: *"Garage Pro keeps the original receipt attached to this entry."* Do NOT bypass the existing gate. Entitlement truth stays server-side.

## 7. Golden-eval plan (committed P0 scope — the accuracy instrument)

`CloudFunctions/scripts/receiptGoldenEval.ts`, modeled line-for-line on `voiceGoldenEval.ts`:

- **Imports prod exports** — `SYSTEM_PROMPT`, `RECEIPT_ENTRY_TOOL`, few-shot builder, `sanitizeReceiptProposal`, `toolInputFromPayload` from `../src/functions/receiptQuickAdd` — so the eval **cannot drift from prod**. (G5)
- **Corpus: ~18 committed SYNTHETIC receipts** under `CloudFunctions/scripts/golden/receipts/` + `manifest.json`, generated by committed `makeGoldenReceipts.ts` (HTML render → JPEG, plus recorded degradation steps: blur, fade, skew, low-light). Zero real PII in git. (G6) Cases: clean dealer invoice with mileage · thermal-faded gas-station receipt · skewed phone photo · handwritten-total small shop · parts-store receipt (isDiy) · tire invoice with road-hazard lines · 2-page invoice (2 image blocks) · tall 3:1 thermal receipt (the P1-VisionKit/tiling evidence case) · **RO#-printed-beside-Mileage trap** · **subtotal-vs-total stack trap** · discount-line case · VIN-prominent dealer case · payment-due-vs-service-date trap · date-free receipt (referenceDateLine check) · decade-old backfill receipt · PDF invoice · non-receipt control (dog photo → `documentLooksLikeReceipt=false`) · few-shot-transfer A/B anchor.
- **Scoring:** per-case expected `{ entryType[], cost, odometerReading, shopName, entryDay, lineItemsContain[] }`, field-by-field, money fields (cost) reported as a separate sub-score; `--runs 3`, `--variant` for prompt A/B (including few-shot ON/OFF — vision transfer is validated, not assumed), `--model` for tier comparison; JSON report to `reports/receipt-golden-*.json`.
- **Gates (pre-registered):** run before/after ANY prompt/schema/model change — a drop is a regression regardless of plausibility. Model escalation to `claude-sonnet-4-6` only if, after prompt iteration plateaus, Haiku scores **<90% overall field accuracy** or a costlier model beats it by **>5 points on the money field**. Measured by outcome, not vibes.
- **Ship gate:** W1 does not deploy until the eval reports ≥90% on Haiku (or the escalation fires and Sonnet clears it — see death condition D1).

## 13. Death condition (pre-registered — what kills or reworks this feature)

- **D1 — KILL BEFORE CLIENT BUILD:** if, after one full prompt-iteration cycle in Wave 1, the golden eval scores **<85% overall field accuracy even on `claude-sonnet-4-6`** (or the money field <90% on both tiers), the vision approach is not viable at acceptable cost — stop; Wave 2 is never built. (Cheap to test: eval runs before any client code exists.)
- **D2 — REWORK:** in the first 30 days post-release, if the field confirm rate `receipt_entry_confirmed / receipt_proposal_succeeded` is **<60%** (users discard the majority of prefills — lab accuracy is not surviving real receipts), freeze the entry point's rollout and run the P1 accuracy track (failure-taxonomy eval cases → prompt cycle 2 → VisionKit/model escalation per §7 gates). If a second cycle still cannot reach 60%, kill.
- **D3 — KILL THE SURFACE:** if after 60 days `receipt_capture_started` is fired by **<3% of weekly-active users** AND the `receipt_scan` paywall source shows zero attributable conversions, the feature is dead weight on the picker — remove the row, keep the server function dark (constants, quota docs, and eval remain for a future re-entry).
- Measurement sources are already in this plan: the closed-enum funnel (§6) and the committed eval reports (`reports/receipt-golden-*.json`). No new instrumentation is needed to execute the death condition — by design.
